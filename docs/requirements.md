# dummy_data_gen 機能拡張 要件定義書

## 0. 文書情報

- 対象プロジェクト: dummy_data_gen（Rust製 CLI ダミーデータ生成ツール）
- 作成日: 2026-09-14
- 版: v0.1（ドラフト）
- ステータス: 検討中（優先度・詳細仕様は今後の実装相談で確定）

## 1. 背景・目的

dummy_data_gen は、YAML設定ファイル（`schema.yaml`）に列定義を記述し、CSV または SQL の INSERT 文としてダミーデータを出力する Rust 製 CLI ツールである。Dr.Sum や MotionBoard といった日本の業務システム向けの検証データ作成を主な用途としている。

現状は列タイプ・出力形式・データ間の整合性チェックといった面で対応範囲が限定的であり、実務での利用シーンに対して機能が不足している。本書では、当面のCLI拡張として実装したい機能を整理し、将来的にはコマンドライン操作に不慣れな担当者でも日本語入力ベースで直感的にデータ定義を組み立てられるツールへと発展させるための土台とする。

## 2. 現状（As-Is）

- 実行方法: `cargo run -- --config schema.yaml --encoding utf8 --format csv --seed 42`
- 列タイプ: `sequence` / `name_ja` / `email` / `integer` / `float` / `boolean` / `date` / `postal_code` / `phone_ja` / `address_ja`
- 出力形式: CSV（`output.csv`固定）/ SQL（`output.sql`固定、INSERT文、`table_name`必須）
- 文字コード: UTF-8 / Shift-JIS(CP932)
- 行ごとに独立したシード付き乱数（SmallRng）により、再現性を保ちながら rayon で並列生成
- バリデーション: min>max、不正な日付、null_rateの範囲外、**列名の重複**などを検知（※列「名前」の一意性チェックであり、F4-1で提案する列「値」の一意性制約とは別物）

## 3. 今回のスコープ

- 対象: 既存CLIツールの機能拡張（列タイプ／出力形式／CLIオプション／データ整合性）
- 対象外: 自然言語入力・GUI化（→ 7章「将来ロードマップ」に記載し、今回は仕様化しない）

## 4. 機能要件

### 4.1 列タイプの追加

| ID | 機能 | 概要 | 優先度 | 状況 |
|----|------|------|--------|------|
| F1-1 | enum型列 | YAMLで選択肢のリストを指定し、その中からランダムに1つを選ぶ列タイプ（例：会員ステータスに「利用中」「休止中」「退会済み」をランダムに割当） | 高 | 実装済み |
| F1-2 | company_name_ja | 「株式会社〇〇商事」のような日本語のダミー会社名を生成する列タイプ | 中 | 実装済み |
| F1-3 | uuid | UUID v4形式のランダムな識別子文字列を生成する列タイプ | 中 | 実装済み |
| F1-4 | katakana_name | 氏名のフリガナ（カタカナ）を生成し、name_ja列と対になる値として扱う | 低 | 実装済み |

### 4.2 出力形式の追加

| ID | 機能 | 概要 | 優先度 | 状況 |
|----|------|------|--------|------|
| F2-1 | JSON出力 | 1行1件をJSON形式で書き出す出力形式を追加（`--format json`） | 高 | 実装済み |
| F2-2 | Excel(xlsx)出力 | Excelでそのまま開けるファイル形式での出力に対応（`--format xlsx`） | 中 | 実装済み |
| F2-3 | Parquet出力 | 分析基盤（BigQuery等）向けの列指向形式。需要が明確になった時点で再検討 | 低（見送り候補） | 未着手（見送り継続） |

### 4.3 CLIオプション／出力先の拡張

| ID | 機能 | 概要 | 優先度 | 状況 |
|----|------|------|--------|------|
| F3-1 | 出力先パスの指定 | `--output` オプションで保存先パス・ファイル名を指定可能にする（現状は`output.csv`/`output.sql`に固定） | 高 | 実装済み |
| F3-2 | 進捗表示 | 大量行を生成する際、コンソールに進捗（件数・割合）を表示する | 中 | 実装済み |
| F3-3 | 複数形式／複数ファイルの同時出力 | 1回の実行でCSVとJSONなど複数形式を同時に出力できるようにする | 低 | 実装済み |

### 4.4 データ整合性・関連性

| ID | 機能 | 概要 | 優先度 | 状況 |
|----|------|------|--------|------|
| F4-1 | unique制約 | 指定した列内で値が重複しないことを保証する設定を追加する（現状はnull_rateのみ指定可能） | 高 | 実装済み |
| F4-2 | 同一テーブル内の列間整合性 | 例：都道府県列が「東京都」なら市区町村列も東京都内の地名になるよう対応関係を保つ | 中 | 実装済み |
| F4-3 | テーブル間の外部キー整合性 | 複数テーブル（ファイル）を生成する際、子テーブルの外部キー列が親テーブルに実在するIDのみを参照するようにする | 低（将来フェーズ） | 実装済み |

## 5. 非機能要件

- 既存の性能特性（rayonによる並列生成、SmallRngによる再現性）を損なわないこと
- 既存のCLI引数・schema.yamlの記述に対する後方互換性を維持すること（既存のschema.yamlがそのまま動作すること）
- 「差分最小の原則」（大規模リファクタ・新規レイヤ導入の禁止）をCLAUDE.mdの方針通り踏襲すること

## 6. スコープ外・保留事項

- 自然言語入力によるスキーマ生成
- GUIフォームでの日本語ラベル選択（→ 将来ロードマップに記載）
- Parquet出力（需要次第で再検討。今回のスコープでは見送り）

F4-3（テーブル間の外部キー整合性）は、当初「複数ファイル生成の設計が前提となるため将来フェーズ」としていたが、2026-09-15にschema.yamlへ`tables:`（複数テーブル）形式を追加する形で実装した。既存の単一テーブル形式は`tables:`を使わなければ完全に後方互換（バイト単位で出力が変わらないことを実測で確認済み）。

## 8. 優先度サマリ

- 高: enum型列（F1-1）／JSON出力（F2-1）／出力先パス指定（F3-1）／unique制約（F4-1）
- 中: company_name_ja（F1-2）／uuid（F1-3）／Excel出力（F2-2）／進捗表示（F3-2）／列間整合性（F4-2）
- 低: katakana_name（F1-4）／Parquet出力（F2-3）／複数形式同時出力（F3-3）／外部キー整合性（F4-3）

## 9. 未決事項（次回相談したい点）→ すべて解決済み

- enum型のYAML記法 → **均等ランダムのみ採用**（重み付けは非対応）
- unique制約が指定件数に対して選択肢が不足した場合の挙動 → **エラーで停止**（重複の黙認はしない）
- 列間整合性（都道府県⇔市区町村）の対応表をどこまでの粒度で持つか → 都道府県5件×市区町村5件程度の簡易な固定テーブル（`CITIES_BY_PREFECTURE`）で実装。`address_ja`（1列）と`prefecture_ja`+`city_ja`（2列）の両方で共有
- `--output` 指定時の拡張子自動推測 → **常に`--format`で明示指定**する方式を採用（拡張子からの自動推測はしない）。複数形式同時出力（F3-3）時は`--output`を拡張子なしのベース名として扱う

F4-3実装時に追加で決定した事項:
- 複数テーブルのschema.yaml形式は、新しいトップレベル`tables:`リストに統一（既存の単一テーブル形式は自動的に1テーブルの`tables:`として扱う後方互換設計）
- 外部キー(`foreign_key`)は`unique`や、参照先列の`null_rate`とは併用不可（併用したい場合はenum/integer等のuniqueで代替を検討）
